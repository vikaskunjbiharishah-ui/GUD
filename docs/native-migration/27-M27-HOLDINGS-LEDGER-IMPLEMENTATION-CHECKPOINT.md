# M27 holdings and ledger — as-built source checkpoint

Date: 12 October 2026. Repository: `vikaskunjbiharishah-ui/GUD`, target `main` only. Milestone: [#5](https://github.com/vikaskunjbiharishah-ui/GUD/issues/5). **Status: substantial implementation committed, not fully scope-accepted; do not close.** This is neither a passing CI report nor a device/security certification.

## Changes actually committed
- **Eight canonical categories with source-exact subcategory labels:** `ManualAssetOnboarding.kt` now retains historical aliases while new Compose registration uses the eight original v9 categories and `src/types.ts` subcategory names. `VaultRepository.registerDetailedAsset` and SQLCipher persist zero-quantity unknown-cost category/subcategory atomically after fresh OS approval, with optional same-owner open custody account; CAMS/KFINTECH fund identity still requires the separate verified CAS enrollment.
- **Extended encrypted profiles:** `core/model/HoldingProfile.kt`; `VaultRepository.holdingProfiles/updateHoldingProfile`; `SqlCipherVaultRepository.kt` and `HoldingProfileEditor.kt`. Protected edits and reads include the full 36-key original `HoldingDetails` inventory, validated scalar types, notes/location, ISIN/symbol, recorded acquisition date, verified/unknown cost status (including explicit correction back to UNKNOWN) and priced quote with source/as-of. Original `Holding`-level typed fields are now exposed through `HoldingRichMetadataContract.kt`: benchmark/issue prices, coupon and interest rates, next coupon/maturity dates, institution, masked account, EMI/count/status, 2018 FMV, taxonomies, tags and allocation percentages. Those fields use scaled-integer/basis-point/date/text/array validation; the original v9 `HoldingDetails` are merged rather than replaced. Unknown historical JSON keys survive merges; immutable CAS identity cannot be silently remapped. Archive is reversible. Closure demands no outstanding ledger units, snapshot units or recorded liability, and is represented separately from archive in encrypted metadata.
- **Ten user-initiated kinds:** `ManualTradePlanner.kt`, `ManualTradeScreen.kt`, `ManualTradeViewModel.kt` and the pre-existing transactional repository gate support BUY, SELL, OPENING_BALANCE, BONUS, SPLIT, DIVIDEND, INTEREST, REPAYMENT, VALUATION_UPDATE and CORRECTION. SNAPSHOT_ADJUSTMENT remains outside the user picker. Corrections are append-only and name one original event; the planner refuses a repeated/cross-owner/snapshot supersession and reruns chronological FIFO. Explicit valuations update the holding's stored quote and provenance in the same SQLCipher transaction. Archived or closed holdings cannot be posted to through `commitManualTrade`.
- **Holdings drilldown:** `CustodyHoldingScreen.kt` includes name/category/subcategory searching, family selection, category and closed/archive filters, linked account display, cost and quote provenance, full per-holding immutable event timeline and protected detail edit.
- **Tests committed, not yet executed:** `ManualTradePlannerTest.kt`, `FinancialGoldenTest.kt`, `NativeCustodyHoldingInstrumentedTest.kt`, `NativeManualTradeInstrumentedTest.kt`, plus existing protected ViewModel fixture adjustments. Cases include kind validation, correction, negative FIFO, split/bonus, net-of-fee sale gain, exact original key round-trip, rate/EMI/tag round-trip, same-owner custody acceptance, owner rollback, archive prevention, dated valuation and password-encrypted portable backup restoration of edited holding profiles. `security_preflight.py` expected routes include the three newly approved native repository methods.

Asset-specific create wizard currently enrolls category/subtype/name/optional owned account; the extended form edits happen after enrollment.

Treat the source as unverified until exact-SHA workflow evidence is green; the physical handset gate remains owner-deferred to M34. Do not mark M27 issue #5 complete before these gaps are resolved.
